# Benchmarking on NVIDIA GB10 (DGX Spark and similar)

What is special about a GB10 machine (NVIDIA DGX Spark and OEM boxes with the same chip) and how to read the
benchmark's numbers on it. To install and serve models with the `gb10` profile, see [setup/README.md](../setup/README.md).

## 1. What is different about GB10

| Feature | What it means in practice |
| --- | --- |
| ARM CPU (`aarch64`) | x86 wheels and images do not work. You need `linux/arm64` builds: NGC containers, PyTorch wheels from the `cu130` index, conda-forge. A package without an arm64 wheel builds from source (slowly) or not at all. |
| Blackwell GPU, `sm_121`, CUDA 13 | Builds without `sm_12x` support fail with "no kernel image". Use CUDA 12.9+ (13.0 recommended) and PyTorch from `https://download.pytorch.org/whl/cu130`. JIT kernels (FlashInfer in vLLM) need `nvcc` from a CUDA 13 toolkit. |
| Unified memory, 128 GB shared by CPU and GPU | There is no separate VRAM. vLLM's `--gpu-memory-utilization` is a fraction of **all** memory (about 119 GiB visible), and every process (OS, page cache, other models, the benchmark) takes from the same pool. |
| `nvidia-smi` memory | Often shows "Not Supported" for used memory. Use `free -g`; the benchmark logs system RAM (`ram_used_gb` in `monitor.csv`) for this reason. GPU utilization and power are still reported. |
| Memory bandwidth ~273 GB/s (LPDDR5x) | Single-user decode is bandwidth-bound, not compute-bound. See section 5. |
| FlashAttention 2 | Does not build for `sm_121`. Use `attn_implementation="sdpa"` in transformers; vLLM picks its own attention backends. |
| torchaudio | Missing from NVIDIA PyTorch containers, and a plain `pip install torchaudio` brings a CPU build. Install it together with `torch` from the `cu130` index. |
| Page cache | Downloaded weights stay in the Linux page cache, which is the same memory the GPU needs. vLLM may fail its startup memory check or hang while loading. Free it before starting large models (section 3). |

## 2. Checking the machine

```bash
uname -m                              # aarch64
cat /etc/os-release | head -3         # usually DGX OS (Ubuntu 24.04)
nvidia-smi                            # GPU name NVIDIA GB10, driver and CUDA version
free -g                               # ~119-128 GB total
df -h ~                               # 100+ GB free for environments and models
nvcc --version 2>/dev/null || ls /usr/local/cuda*/bin/nvcc   # CUDA toolkit for JIT kernels
python3 -c "import torch; print(torch.__version__, torch.cuda.get_device_capability())"   # (12, 1)
```

With Docker, check that containers see the GPU:
`docker run --rm --gpus all nvidia/cuda:13.0.0-base-ubuntu24.04 nvidia-smi`. If that fails, configure the NVIDIA
Container Toolkit (preinstalled on DGX OS):
`sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker`.

A rented GB10 in an unprivileged container (no sudo, no Docker) is covered in
[setup/README.md](../setup/README.md#rented-gb10-in-an-unprivileged-container).

## 3. Serving models

### Memory budget

Each vLLM process reserves its `--gpu-memory-utilization` share of the whole memory for weights plus KV cache, and all
processes together with the OS must fit. An example for a voice pipeline:

| Process | Fraction | ≈ GB |
| --- | --- | --- |
| LLM, 8B in FP8 | 0.25 | 30 (weights ~9 + KV cache) |
| ASR, ~2B | 0.08 | 10 |
| TTS, NLU (plain PyTorch) | — | 2-5 |
| OS, benchmark, headroom | — | the rest |

Start vLLM processes one at a time, largest first. A BF16 model needs roughly twice the weight memory of FP8.

### Page cache

`setup/serve.sh` frees it before every start on the `gb10` profile. By hand, with root (NVIDIA's recommendation
before starting vLLM): `sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'`. Without root, evict only the files
you own, e.g. the Hugging Face cache:

```bash
python3 - <<'EOF'
import os
for root, _, files in os.walk(os.path.expanduser("~/.cache/huggingface")):
    for name in files:
        try:
            fd = os.open(os.path.join(root, name), os.O_RDONLY)
            os.posix_fadvise(fd, 0, 0, os.POSIX_FADV_DONTNEED)
            os.close(fd)
        except OSError:
            pass
EOF
```

### LLM in the NGC container

The alternative to the setup scripts. Newer tags need newer drivers (tags from 26.04 require driver 595.58+; on an
older driver use an older tag or update DGX OS):

```bash
docker run -d --name llm --gpus all --ipc=host \
  --ulimit memlock=-1 --ulimit stack=67108864 \
  -p 8000:8000 -v ~/.cache/huggingface:/root/.cache/huggingface -e HF_TOKEN \
  nvcr.io/nvidia/vllm:<tag> \
  vllm serve Qwen/Qwen3-8B-FP8 --host 0.0.0.0 --port 8000 \
    --gpu-memory-utilization 0.25 --max-model-len 8192 \
    --enable-prefix-caching --max-num-seqs 32
```

For Qwen3 and other reasoning models measured as a voice assistant, turn thinking off in the benchmark config:
`extra_body: {chat_template_kwargs: {enable_thinking: false}}`.

### ASR

vLLM serves speech models (Whisper, Qwen3-ASR and others) on `/v1/audio/transcriptions`, which `asr: type: openai`
calls directly. Audio decoding needs `librosa` and `soundfile`; pin torch/vLLM so pip does not replace them:

```bash
pip freeze | grep -E '^(torch|torchvision|vllm)==' > pin.txt
pip install -c pin.txt librosa soundfile
```

If a model's own package does not support the platform, look for a community build for DGX Spark (for Qwen3-ASR,
`qwen-asr-dgxspark` on PyPI).

### TTS, NLU and other PyTorch models

Most TTS and classifier models have no standard server. Wrap them in a small HTTP service (FastAPI is enough) that
takes `{"text": ...}` and returns WAV bytes or `{"intent": ...}`, then use the benchmark's `http` type, or write a
plugin. On GB10:

- install `torch` and `torchaudio` in one command from the `cu130` index;
- pin them (`pip install -c pin.txt ...`) when installing the model package, or it may pull a different torch;
- use `attn_implementation="sdpa"`;
- `torchaudio` loads audio through `torchcodec` and ffmpeg: install both.

A small classifier runs fine on the 20 Grace CPU cores if you want to keep memory for the LLM.

## 4. Reading the results

- Run `bench.py` on the GB10 itself so the monitor sees the machine. `ram_used_gb` in `monitor.csv` is the GPU memory
  too; the `idle` phase is the baseline with the models loaded, so peaks above it are what the run itself used.
- The pipeline load test shows how much ASR and TTS slow the LLM: all of them share one memory bus.
- Compare precisions as separate runs: serve the model in FP8 and run with `--machine gb10-fp8`; restart it in BF16
  (raise `--gpu-memory-utilization`), change `llm.model`, run with `--machine gb10-bf16`.

## 5. What to expect: decode is bandwidth-bound

Generating one token for one user reads all model weights from memory once, so single-user decode speed is at most
roughly

```
tokens/s ≈ memory bandwidth / bytes of weights read per token
```

For GB10 (~273 GB/s) and an 8B dense model that gives about 17 tokens/s in BF16 (~16 GB) and about 32 tokens/s in
FP8 (~8.5 GB); real numbers land below that, and a long context lowers them further because the KV cache is read too.

- Quantization (FP8, 4-bit) speeds up decode almost in proportion to the size reduction; extra compute does not help.
- Mixture-of-experts models read only the active experts per token, so they decode much faster than a dense model of
  the same total size.
- Batching is cheap: weights are read once per step for the whole batch, so total tokens/s grows with concurrency
  while per-user speed falls slowly. The load test shows where per-user speed crosses your thresholds.
- Prefill (TTFT on a long history) is compute-bound and scales differently from decode; check both.
- Against a desktop GPU with ~1-1.8 TB/s of GDDR bandwidth, expect several times slower single-user decode, but far
  more memory for large models and many processes at once.

## 6. Common problems

Install and serve errors from the setup scripts are in [setup/README.md](../setup/README.md#troubleshooting).

| Symptom | Cause | Fix |
| --- | --- | --- |
| vLLM container prints `compatibility mode is UNAVAILABLE` | driver older than the container needs | update DGX OS / driver or use an older container tag |
| vLLM runs out of memory or hangs at startup | page cache fills the shared memory, or the fractions add up to too much | free the cache, lower the fractions, start services one by one |
| `no kernel image is available for execution` | library built without `sm_121` | use `cu130` wheels / NGC containers, CUDA 12.9+ |
| `pip install` pulls x86 wheels or builds for hours | no arm64 wheel for that package | look for arm64 wheels or conda-forge, use NGC containers |
| `torchaudio` has no CUDA or fails to import | installed from the wrong index | `pip install torch torchaudio --index-url https://download.pytorch.org/whl/cu130` together |
